# 面向 Agent 维护的「复杂度」指标设计

状态：提案 v0.1（2026-09-19）。原型已在本仓库 dsh-code v0.7.22 上实测（数据见第 4 节）。
方法论：先定成本模型，再定义可观测量，最后给出可证伪的验证实验。指标本身不是目标。

## 0. 一句话结论

经典复杂度（cyclomatic / cognitive）测量的是「一个函数内部有多少条路径」，而 agent 的维护成本取决于三件它没测的事：**做一次正确改动要驻留多少信息（读入半径）、本地改动会牵动多少处（联动半径）、改错了能不能被机器拦住（检出能力）**。把这三件事加进来，排序会显著变化——本仓库实测中，一个只有 31 个决策点、却被 44 处字符串锚点隐式耦合的构建脚本，排到了风险第 3 位。

## 1. 第一性原理：agent 维护的成本结构

### 1.1 维护单元是任务，不是函数

人类审查以函数/类为单位。Agent 接到的是**任务**（"加一个 TUI 命令"、"改一处错误提示"），任务的落点跨函数、跨文件。因此以函数为分母的复杂度指标，度量单位与 agent 的工作单位不匹配。

### 1.2 成本模型

设 agent 完成一次维护任务 τ，其期望代价：

    EC(τ) = R(τ) + P_fail(τ) · (1 − D(τ)) · C_regress(τ)

- `R(τ)`：正确完成 τ 必须读入上下文的信息量（token）。这是**硬约束**——超过窗口就得截断、摘要或猜，直接掉正确率。
- `P_fail(τ)`：产出的补丁语义错误的概率。
- `D(τ)`：错误被机械拦住的概率（类型检查、测试、独立评审）。
- `C_regress(τ)`：未检出错误的回归代价。

关键判断：**P_fail 无法直接优化（它是模型能力的函数），但 `R` 和 `D` 是代码属性的函数。** 所以「面向 agent 的复杂度」应该测量 `R`、以及 `P_fail` 中**由代码结构造成的那部分**、以及 `D` 的缺口。

### 1.3 P_fail 的分解（代码侧的四条机制）

| 机制 | 含义 | agent 的典型失败 |
|---|---|---|
| 隐藏耦合 | 编辑点所需的知识在引用图之外（字符串锚点、约定命名、注册表、`any`） | 改对了本地，漏掉了远处的隐式契约 → 静默失效 |
| 联动半径 | 一次逻辑改动必须同时改 N 处 | 改了 3 处漏了第 4 处 → 半成品补丁 |
| 路径数 | 单元内独立分支数（= 经典 cyclomatic 的合法内核） | 改了主路径，漏了边角分支 |
| 共享状态 | 跨单元的隐式可变状态（hooks、全局注册表） | 破坏不变量，类型全对、行为全错 |

### 1.4 检出能力的缺口（D）

同一条错误，代价差一个数量级：
- 有类型检查 → 编辑时就红；
- 有测试 → 提交前红；
- 都没有 → 上线后由用户发现。

本仓库的真实案例：vendored 终端的 `app.ts` 调用了未导入的 `wrapText`，是 `ReferenceError`；这**本可被 tsc 一秒拦下**，但该文件此前不在任何编译器的视野里（Node 只擦除类型、`ts.transpileModule` 只看语法、ESLint 只匹配 `*.mjs`）。所以 `D` 不是修饰项，它是乘数。

## 2. 指标定义

### 2.1 R：编辑半径（Read Radius）

    R(u) = tokens(u) + Σ tokens(importer ∈ 直接消费者(u))

含义：改 `u` 的一个导出，理论上要把消费者的期望一起放进上下文。

**实测（本仓库，tokens ≈ 字符数/4）**：

| 单元 | 自身 | 直接消费者 | 编辑半径 |
|---|---|---|---|
| `packages/tui/src/render/status.ts` | 8,642 | 6 | **248,171** |
| `packages/tui/src/provider-settings.ts` | 9,421 | 3 | 225,347 |
| `packages/tui/src/store.ts` | 1,520 | 4 | 219,636 |
| `packages/tui/src/i18n.ts` | 806 | 13 | 177,454 |
| `packages/tui/src/app.ts` | **93,484** | 2 | 151,400 |

读法：`status.ts` 自身只有 8.6k token，看起来无害；但它是 hub，改它的导出理论上要触及 24.8 万 token 的消费者。Agent 不会真读完，于是变成"猜消费者的期望"——这正是 hub 模块改动事故率高的机制。`app.ts` 则是另一种病：单个文件 93k token，一次全读就吃掉整个工作集。

### 2.2 B：联动半径（Blast Radius，经验值）

    B(u) = 与 u 高频共同改动的文件数（git 共同改动，阈值 ≥ 2 次）

这是**测出来的耦合**，不是猜的，天然包含引用图看不到的一致性约束（文档、测试、package.json、prompt 列表）。

**实测**：

| 文件 | 改动次数 | 高频共同改动 |
|---|---|---|
| `scripts/patch-runtime.mjs` | 16 | `tests/dscode.test.mjs` 14、`scripts/build-packages.mjs` 12、`docs/CHANGELOG.md` 9、`docs/tui-commands.md` 9 |
| `scripts/build-packages.mjs` | 22 | `README.md` 14、`package.json` 12、`patch-runtime.mjs` 12、`tests/dscode.test.mjs` 12 |
| `plugins/dscode/index.mjs` | 8 | `tests/dscode.test.mjs` 8、`docs/dscode-ultra.md` 6、`patch-runtime.mjs` 6 |

结论：改一次 runtime patch，经验上是一个 **4–5 文件的任务**，不是 1 个文件。任何"函数级复杂度"都不会告诉你这件事。

> 口径警告：release 提交会把 CHANGELOG/package.json/README 打包进来，所以与它们的共现含噪声。应优先采信与 `tests/*`、源码的共现。

### 2.3 H：隐式耦合（Hidden Coupling）

    H(u) = 不可见于引用图的边 / (显式边 + 不可见边)

可静态识别的不可见边：字符串锚点（`replaceOnce(text, '锚点', …)`）、按字符串拼路径的模块加载（`join(root,'plugins',name,'index.mjs')`）、动态 `import()`、`any` 边界、约定式命名经注册表解析。

**实测**：`scripts/patch-runtime.mjs` 有 **44 处** 字符串锚点/动态加载；而它的 `replaceOnce` 会在 `split(from).length !== 2` 时抛错——这是本仓库最值得称赞的设计，因为**它把不可见耦合变成了显式失败**。改造建议同理：凡是隐式耦合，最好都配一个"锚点失效即抛错"的断言。

### 2.4 U：未验证路径（Unverified Decisions）

    U(u) = D(u) × (1 − coverage(u))

其中 `D` 是决策点数（if / 三元 / for / while / case / catch / `&&` / `||` / `??`），coverage 是行覆盖率。

含义：**不是"有多少条路径"，而是"有多少条路径既没被测、又没被类型区分"**。同样是 D=50，覆盖率 95% 的单元和 0% 的单元，agent 的期望失败率不是一个量级。

**实测（Top）**：

| 文件 | 决策点 D | 覆盖率 | 未验证 U | 改动次数 |
|---|---|---|---|---|
| `packages/tui/src/app.ts` | 2,737 | 未测（.ts） | 2,737 | 5 |
| `packages/tui/src/kernel-panels.ts` | 558 | 未测 | 558 | 1 |
| `packages/tui/src/index.ts` | 528 | 未测 | 528 | 4 |
| `packages/tui/src/render/projection.ts` | 487 | 未测 | 487 | 3 |
| `plugins/tui-tools/index.mjs` | 158 | 72% | 45 | 10 |
| `scripts/build-packages.mjs` | 23 | 0% | 23 | 22 |
| `scripts/publish-hub.mjs` | 61 | 0% | 61 | 6 |

注：`.ts` 的 coverage 未纳入统计（见 `docs/maintainability.md`），因此按最坏情况计 U=D；若按"tsc 已能拦截类型错误"折算，U 应乘以一个类型不可区分的分支占比——这需要分支级类型分析，属于后续工作。

### 2.5 C：检查存在性（二值门，不是分数）

    C(u) = 1，若 u 被类型检查或行为测试读取；否则 0

**任何 `C(u)=0` 且 `D(u)>20` 的单元，优先级高于一切复杂度优化。** 本仓库上一轮修的 31 个类型错误里，`wrapText` / `formatTokens` 两个真实崩溃都落在这一类。

### 2.6 复合排序（用于排优先级，**不得作为优化目标**）

    AMC(u) = (U(u) + 1) × (1 + H(u)) × (1 + churn(u))
    Gate(u) = R(u) > 上下文预算 或 C(u) = 0 且 D(u) > 20

**实测复合排序（本仓库）**：

| 排名 | 单元 | D | U | H | churn | AMC |
|---|---|---|---|---|---|---|
| 1 | `packages/tui/src/app.ts` | 2,737 | 2,737 | 0 | 5 | 16,428 |
| 2 | `packages/tui/src/index.ts` | 528 | 528 | 0 | 4 | 2,645 |
| 3 | `scripts/patch-runtime.mjs` | 31 | 2 | **44** | **16** | 2,295 |
| 4 | `packages/tui/src/render/projection.ts` | 487 | 487 | 0 | 3 | 1,952 |
| 5 | `scripts/build-packages.mjs` | 23 | 23 | 2 | **22** | 1,656 |
| 6 | `packages/tui/src/kernel-panels.ts` | 558 | 558 | 0 | 1 | 1,118 |

第 3 名是**这套指标相对经典复杂度的核心价值**：`patch-runtime.mjs` 的 cyclomatic 复杂度很低（31），任何传统工具都会判它"简单"；但它的隐式耦合和改动频率把它推到风险前三。

## 3. 为什么这四个轴，而不是别的

| 指标 | 对应的 agent 失败模式 | 可观测后果 | 现状检测手段 |
|---|---|---|---|
| R | 上下文截断 → 凭想象写消费者 | 补丁局部正确、契约错误 | 无（可静态计算） |
| B | 多站点改动漏改 | 半成品补丁 | 无（git 共现可测） |
| H | 隐式契约失配 | 静默失效，测试全绿 | 部分（锚点断言可补） |
| U | 边角分支被改坏 | 回归 | 覆盖率已有，需乘 D |
| C | 错误无人拦 | 崩溃/回归直达用户 | 已有（typecheck / tests） |

对照经典指标：
- **cyclomatic = U 的未归一化代理**。缺 `(1−coverage)` 修正，也缺"类型能否区分这两个分支"的维度。
- **cognitive complexity = R 的一个局部近似**（嵌套越深，理解该函数需要的驻留信息越多），但只覆盖函数内，不含跨文件的消费者期望。
- 两者都**不含 B 和 H**，而实测中正是 B/H 决定了 `patch-runtime.mjs` 的排序。

### 3.1 还要补一个「任务级」指标

因为任务是跨函数的，函数级指标必须能聚合到任务级：

    TR(τ) = |必需触及的站点集合|        （联动广度）
    TOK(τ) = Σ R(站点)                  （读入总量）
    PASS(τ) = D(τ) 在各站点的乘积       （检出强度）

`TR(τ)` 可以用 git 共现集估计，也可以用"某类任务的历次提交"学习出来。**这才是给 agent 排任务难度、决定"要不要先补测试再动手"的依据。**

## 4. 验证设计与可证伪性

指标是假设，不是定义。必须能被推翻。

**结果变量（本 harness 可直接测量）**：
- agent 编辑后的测试失败率、`auto-review` 判定（`plugins/auto-review/audit.mjs` 有审计记录）；
- 会话内的回滚/重试次数、用户纠正次数；
- 交付后被后续提交修掉的"补丁的补丁"。

**假设**：
- H1：`U × (1+H) × churn` 对"agent 编辑失败"的预测力 **强于** 裸 `D`（cyclomatic）。
- H2：`R > 上下文预算` 的单元，失败率显著高于其余（且失败模式以"契约错误"为主）。
- H3：`C=0` 的单元引入**崩溃类**缺陷的比率显著更高（本仓库已有 2 例佐证）。

**方法**：取 N 个真实维护任务，随机/自然分配到不同单元，记录结果；对指标做逻辑回归，报告 AUC 与置信区间，而不是只看相关系数。数据来源现成：`session_search` 会话历史 + auto-review 审计 + git 历史。

**防 Goodhart**：指标只用于**排护栏优先级**，不直接作为重构目标。禁止"为降 AMC 而拆函数"——那会破坏局部性（见 §5），把 agent 逼成跨更多文件拼装逻辑。

## 5. 局限与已知偏差

1. `tokens ≈ chars/4` 是粗估，中英混排偏差更大；应用真实 tokenizer。
2. `R` 只算直接消费者，未传递闭包；H 的"不可见边"是启发式识别，会漏（正则匹配不到的动态派发）。
3. `B` 被 release 提交污染（CHANGELOG/package.json/README 常与任意源码共现）；应做"排除发布产物"的二次统计。
4. `U` 只在被测试加载过的文件上有 coverage；未加载文件按 0 计，偏保守。
5. `.ts` 的类型可区分性未建模，`U` 对易被 tsc 拦截的错误高估。
6. 指标对**同一仓库的时间序列**有意义，跨仓库比较需要归一化（tokens、churn 窗口）。

## 6. 落地顺序（按 ROI）

1. **先补 C**：给零检查的区域上类型检查/测试（本仓库已完成 tsconfig + typecheck）。
2. **再补 H 的失败显式化**：隐式耦合处加锚点断言；本仓库的 `replaceOnce` 已是范例。
3. **修 R 的两个极端**：`app.ts`（93k token 单文件）与 hub 模块（`status.ts` 半径 248k）——前者拆，后者补契约测试。
4. **U 低门槛起步**：`complexity` warn 15 / error 25、`max-depth` 4，先 warn 观察分布，别让门禁常年红。
5. **B 用于流程**：对高 B 的任务，强制"多站点清单 + 一次性验证"。
6. 只有 1–5 稳定后，才考虑把复合分接入评审。**顺序反了会把资源投在无人区。**
