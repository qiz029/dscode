# DSCODE preset and Ultra

The interactive TUI is fixed to the `dscode` preset. `/new` starts a DSCODE conversation; the preset picker is absent from slash completion and help. Typing `/mode` reports that the preset is fixed, and `/new <other-preset>` or `--mode <other-preset>` is refused. The hidden compatibility flag `--mode dscode` still works. Resuming an older conversation mounts DSCODE while preserving its transcript and recording the new effective preset; the original session header is retained. Model, reasoning effort, permissions and plan mode keep their separate controls.

## Execution through a persistent shell

The preset combines the pinned minimal preset's owner-scoped persistent shell with project instructions, runtime context, Skills, plan/Todo/Goal, compaction and subagents from standard. It does not copy minimal's fixed complete system prompt or its lack of compaction. Host MCP, Computer Use, hooks and auto review remain mounted. Skill and instruction discovery — including the ancestor mode — is described in [Skills](skills.md).

The preset also registers a `review` tool and `/review` command backed by one independent, read-only model request over the selected Git diff. The main agent is guided to call it after code changes and focused checks, before its final reply. This is a diff-only review, not a tool-using subagent or a substitute for tests; it does not change Ultra delegation policy. See [TUI review usage](tui-commands.md).

The persistent Bash shell accepts UTF-8 command arguments and file names, including Chinese, accented letters and emoji, even when the inherited locale is `C`. Its Readline input settings preserve high bytes instead of interpreting them as Meta shortcuts. Command locale settings remain inherited; this does not transcode programs that emit a different encoding. Existing shell sessions need to be recreated after updating.

The model uses dedicated file tools for text files:

| Tool | Behavior |
| --- | --- |
| `read(file_path, offset?, limit?)` | Returns numbered UTF-8 lines with pagination. `offset` starts at 1; a call returns at most 2,000 lines and 50 KiB, with individual lines capped at 2,000 characters. |
| `edit(file_path, old_string, new_string, replace_all?)` | Replaces exact text. The match must be unique unless `replace_all` is explicitly enabled. |
| `edit_many(file_path, edits)` | Terminal/server: applies 1–100 `old_string`/`new_string` pairs to one original file. Matches must be unique and non-overlapping; all replacements are validated before a single atomic write. |
| `write(file_path, content)` | Creates a file or atomically replaces its full contents. Prefer `edit` for targeted changes. |

On the terminal/server runtime, `read` streams only far enough to produce the requested window and detect whether more content remains. `totalLines` is present only when the scan reaches EOF; otherwise `hasMore: true` and a continuation offset replace an exact total. The terminal still displays numbered lines. Repeated reads of the same window and file version reuse a session-local cache, bounded to 32 pages and 1 MiB of serialized entries. File metadata is checked on every call and again before accepting its result. Changed versions miss the cache; changes detected during the read reject the result. Reads near the end still scan the preceding lines on a cache miss; this is not a persistent line index. UTF-8 validation covers the scanned chunks, not an unread tail.

`edit_many` uses the same read-before-edit, version check, sandbox, line-ending preservation and atomic publication as `edit`. It reads and rewrites the full file once per batch, rather than writing only changed disk blocks. An invalid, ambiguous or overlapping replacement rejects the entire batch. This tool is advertised only by a supporting filesystem backend. The separately pinned Desktop runtime retains its existing file tools and read behavior.

Editing or overwriting an existing file requires a prior `read` in the same session. Changes made by another session, editor or shell invalidate the observed version: the operation fails without overwriting them, and the model must re-read and reconcile before retrying. Successful writes and edits refresh that observation, so consecutive edits do not require redundant reads. Creating a new file does not require a prior read and refuses to clobber a concurrently created file. A partial read records the file version; it does not prove that the model has seen the whole file. Observations do not survive session resume. A shell read or search does not establish a file-tool observation.

File-tool relative paths resolve against the session workspace, independently of shell `cd`. The tools use the Host filesystem sandbox and approval mechanism; unread or stale-file rejection is not a reason to bypass the guard through the shell. Read results carry line-window metadata, and edits and overwrites carry diff metadata for the terminal and Desktop views. New-file creation returns a confirmation rather than a result diff. When attachment storage is available, the same plugin also exposes `read_image`; execution requires an image-capable model.

The model keeps `bash` for searches with `rg`/`rg --files`, builds, tests and batch operations. There are no separate `glob` or `grep` tools. `cd`, exports, functions and background jobs persist across calls for the same agent. Each child gets a separate shell and independent file observations. By default children share workspace files; the parent can explicitly set `worktree: true` on `subagent` or `subagent_fork` to give a child an isolated Git checkout.

On the terminal/server runtime, persistent Bash saves results exceeding its inline limit (16,000 characters by default) through the Host spill store before shortening the response. The response includes a preview, exit status and a path that `read` or shell searches can retrieve. Successes, command failures and timeout captures use the same path; timeout captures remain partial. The existing capture window retains at most 4 MiB, and a lost prefix is reported both inline and in the saved file. Redirect a command to a file when a larger complete log is required. Spill files are private temporary files, subject to OS cleanup and the store's default 30-day startup cleanup; they are not permanent artifacts or compressed/deduplicated storage. A storage failure leaves a bounded preview and an explicit retrieval-failure notice. Other tool outputs continue to use the upstream spill policy. This change does not alter PowerShell or `shell_retry` capture limits.

`apply_patch` remains available in the harness shell PATH for multi-file patches and wraps `git apply`. Feed it a **standard unified diff**, not the Codex `*** Begin Patch` format. Git is required. `apply_patch --check` checks hunks without writing. This works outside a Git repository too. It checks patch context, not the file tools' observed versions; shell mutations remain subject to the active OS sandbox.

```sh
apply_patch <<'PATCH'
diff --git a/example.txt b/example.txt
--- a/example.txt
+++ b/example.txt
@@ -1 +1 @@
-before
+after
PATCH
```

`/shell` lists the current session's terminals. `/shell reset` closes them while the agent is idle. Timeout, cancellation, `exit`, reset and host restart discard shell state; the next call starts at the session workspace. Conversation resume restores messages and files, **not** an OS process or its exports. Commands receive EOF on stdin by default; pipelines, heredocs and explicit input redirections still work. The tool waits for the command's completion marker, rather than treating a terminal readiness hint or partial output as completion. Silent work is not interrupted merely because it looks idle. Programs that explicitly open the terminal for interactive input are unsupported and may need cancellation or the command timeout. Background work can use shell job control; `shell_retry` also exposes the existing tracked background-job mechanism.

Normal persistent commands keep the active OS sandbox and do not each incur an LLM review. After a genuine sandbox denial, the model may use `shell_retry` for a single fresh-shell retry, with explicit `workdir`, wider `sandbox_permissions` and justification. This uses the original escalation approval seam and auto reviewer. Reviewer input resolves relative workdir against the session workspace and explicitly identifies the environment as fresh. It cannot see or rely on the persistent shell's exports/functions. Rejected approval prevents execution. Sandbox mode changes while persistent terminals exist are rejected upstream; close them with `/shell reset` first when changing permission modes that also change sandbox policy.

Hooks which should cover both execution paths should match `^(bash|shell_retry)$`.
Hooks that also cover text-file access should include `read`, `edit`, `edit_many` and `write`; include `read_image` for image reads.

## Ultra effort

In the DeepSeek native route, `/effort` replaces the bottom composer with a Low → High → Max → Ultra bar (arrow keys to move, Enter to apply, Esc to cancel, `o` for Off). Focusing Ultra triggers a blue wave that spreads from the center before confirmation. After applying Ultra, the composer briefly shows a second center-out text-and-border ripple. Both effects are skipped when animations are disabled. Ultra is a harness policy, not a new DeepSeek API value:

- Session selection and request headers retain `ultra`; the native adapter serializes it as `thinking.type: enabled` and `reasoning_effort: max`.
- Normal tool-capable requests get collaboration guidance appended to the effective system message at the adapter boundary. The immutable logged request is not mutated. This extra text is reflected in provider usage; preflight local token estimates do not include the adapter-added text.
- The guidance actively seeks independent useful subtasks, disjoint file ownership and independent review, while avoiding delegation for trivial work. The main agent integrates and verifies results.
- Children inherit the effort when no model/effort override is selected. Ultra stays in the persisted request header across compaction and the TUI's standard restore path; switching effort to Max removes the extra guidance on subsequent requests. Switching to a different provider uses that provider's own effort catalog.
- In dscode, a parent can run at most five direct children concurrently below Ultra and twenty at Ultra, judged by the parent's effort when it launches or wakes a child; admission reservations prevent concurrent launches from racing past the cap. Idle-child wake requests also count. The preset allows one delegation level, including non-Ultra sessions. Parent/child messaging remains available; direct sibling messaging is not added.
- Every child gets a parent-chosen `name`: 1 to 10 characters, letters, digits and underscores only, starting and ending with a letter, unique among the parent's live, resumable and starting children. The child appears as `/name · description` in the TUI agents line and `/agents`, and the parent addresses it as `/name` in `send_message` and `interrupt_agent`; a child addresses its parent as `/`. Continuable child names resolve from the parent's saved catalog after a Host restart, and sending to one resumes that same child. Lookup alone does not wake it. In the terminal every child starts in the background: the call returns `started subagent /name (id)` at once and the runtime notifies the parent when the child settles, so a parent that needs the result continues other work or waits for that notice. On the Desktop package (Harness 0.2.0) a call can still wait in the foreground, and a disposed foreground child cannot be resumed by name. Session ids keep working as before.
- Prefer `subagent_fork` when completed conversation history helps the child; use fresh `subagent` for self-contained work that gains nothing from that history. Fork excludes the unfinished turn, so the child's assignment must still state its objective and constraints. Both child paths hide delegation tools, and runtime checks reject a child that tries to delegate again.
- Worktree choice is independent of conversation forking. `worktree: true` creates a detached checkout under `.dscode-worktrees/<id>/` at the parent repository root, starting from `HEAD`. It requires the parent session cwd to be that Git root and the parent worktree to be clean, including untracked files. A dirty parent is rejected before creating a child, so a child never silently misses uncommitted parent changes. Omit the flag for read-only tasks or when the child needs those changes; choose it for independent parallel edits. The child session persists its own cwd; the parent receives the path in the tool result and must inspect and integrate the diff. The checkout remains available for later messages to an idle child; remove it with `git worktree remove PATH` only when no child follow-up or resume is expected. Removing it earlier makes that child's future file work fail. Worktrees with edits are retained on child failure, while an empty checkout is removed if child startup fails. The directory is added to local `.git/info/exclude` so it does not appear as an untracked parent change.
- Every effort can start or wake child agents, so models without a `max` level (which never offer Ultra) can delegate too. Below Ultra there is no collaboration policy; the shell policy makes delegation the exception instead: the agent works itself by default, delegates only a substantial independent part or a broad read-only investigation, runs at most one child at a time and picks the lowest child effort the model offers. This is prompt guidance; the runtime enforces only the five-child cap and the single delegation level. `workflow` and `ralph` are unavailable in this preset because they can start children outside the admission cap.
- Compaction/title requests do not get the collaboration instruction. Auto review does not inherit the main agent's Ultra selection. Permissions are unchanged.

Use Ultra for complex changes with independent investigation/implementation/review opportunities. It is not the default and can cost more tokens because children make additional model requests. `/agents` shows their activity; `/status` and `/review-usage` expose the existing recorded usage surfaces. The native root token totals are not a complete bill for child sessions. The session footer separately aggregates recorded descendant calls; see [session metrics](session-metrics.md).

Normal `deepseek-flash` agent requests also receive a short task-proportional instruction: answer simple questions directly; for bounded code changes, make the focused change, run the relevant check, and stop when it passes. This is guidance rather than a hard reasoning-token limit. Internal compaction and other non-agent calls do not receive it.

## Delegate mode

`/delegate <task>` asks the main agent to coordinate the task instead of doing it. The command only checks that the session starts at a clean Git repository root and then queues the task with a fixed coordinator protocol as the agent's next turn; planning, dispatch, verification and merging are the model following that protocol, while the runtime enforces the child cap and keeps the board. It works at every effort and overrides the below-Ultra one-child guidance for that task.

The main agent first plans the parts on a delegate board with the `delegate_board` tool: each task gets a title, the child name it will run under, its owned files, a priority (`high`, `normal` or `low`) and the tasks it depends on — only those whose changes it must build on. The board rejects dependency cycles. A pending task is ready once every dependency is complete, and blocked until then; the runtime refuses to launch a blocked task. Ready tasks are ordered by effective priority, which is a task's own priority or that of any open task waiting on it, whichever is higher, so work that unblocks a high-priority task goes first. The main agent launches ready tasks in that order, in the background with `worktree: true`, while child slots are free — five below Ultra, twenty at Ultra — and launches the next ones as children settle. Launching a child under a task's planned name moves the task to running. `delegate_board update` re-plans a pending task's priority or dependencies, and dropping a task releases the tasks that waited on it. Whenever the board changes, the main agent receives its state and the number of free slots as a message ahead of its next step, so a free slot with pending work is always in view. The state is not placed in the system prompt, because rewriting the prompt on every change would invalidate the provider's prompt cache for the whole conversation; the terminal hides these board messages, and `/delegate` itself appears as one line.

Children work only in their own worktree and leave their changes uncommitted. A task with dependencies starts from their verified changes: its child applies each dependency's diff from the worktree path the board recorded, then commits the result as a baseline on its worktree's detached HEAD. That commit never reaches a branch; it keeps the child's own diff separate from its dependencies' changes. A child that is blocked sends its question to `/` and waits; its task stays in running, marked as waiting, until the main agent answers with `send_message`. Once a child settles, its task shows as verifying. The main agent verifies tasks that others depend on first, since they gate further work. It reviews the worktree and reruns its checks there, then records the task as complete with the evidence, sends the child fixes, or reopens the task. A task cannot be completed before its child was launched, and the tool requires the verification evidence.

Merging waits until every task is complete or dropped, because a new worktree needs a clean main workspace. Complete tasks are then merged in dependency order, each dependency before the tasks built on it, so a task with a baseline contributes only its own changes. Each is merged with `git -C <worktree> add -A && git -C <worktree> diff --cached --binary | git apply --3way`, which stages the result; nothing is committed, branched or pushed unless you ask. The final reply lists each task's outcome and the checks run in the main workspace.

`/delegate-dashboard` opens the board as a kanban with pending, running, verifying and complete columns. Running and verifying are read from the children's live status, not from what the model last reported, so the board cannot claim a child is working after it stopped. Boards are kept per session under `$DSH_HOME/delegate-boards/` and survive a restart; `delegate_board clear` empties one.

## Implementation and checks

`presets/dscode/agent.cordis.yml` is the checked-in composition template. Setup renders it as one `@deepseek-ai/dsh-agent-preset` declaration row at the end of the profile patch, with its plugin paths resolved; DSH 0.1.7's preset registry reads declaration rows and no longer discovers presets from a directory. The launcher performs idempotent, version-checked patches to the pinned native DeepSeek adapter (Ultra), bash tool (separate name for retry), persistent shell (reset cache invalidation), and DSH-Code TUI (existing `/clear`/command discovery fixes). Unsupported upstream package versions or source shapes fail setup. These changes are included in the full tar distribution; the Hub-only configuration export does not include them.

Tests cover real serialized DeepSeek requests with mocked HTTP, concurrent admission reservations, persistent cwd/exports, unified-diff file editing, fresh retry isolation, approval denial, cancellation/reset, actual child shell isolation, deterministic manual compaction and TUI-equivalent Ultra restoration. The actual terminal picker was also checked for Ultra and the default dscode mode. These are local deterministic checks, not a paid DeepSeek quality or multi-agent performance benchmark.

### Task-proportional execution

Ultra keeps native `max` reasoning but now explicitly routes bounded work (such as one unit test) through direct implementation and focused verification. It avoids unnecessary planning, child agents, broad repository scans and repeated review. Expand scope only for a concrete uncertainty or failure; stop when acceptance criteria and required checks pass. This is prompt guidance, not a runtime deadline or adaptive reasoning-effort switch. It has not yet been benchmarked against the reported slow session, and cannot guarantee shorter model deliberation.

### Per-child reasoning effort

The parent can pass `reasoning_effort` to `subagent` or `subagent_fork`, independently of the model-selection opt-in. For example: `{"name":"unit_tests","description":"Add focused unit tests","prompt":"...","reasoning_effort":"low"}`. Omission keeps existing inheritance. The selected child model validates the effort before child creation; unsupported values fail instead of silently falling back. Effort-only selection does not change provider/model or the parent's effort. Explicit provider/model overrides still require the existing model-selection policy. Ultra guidance asks parents to choose low for bounded work, high for difficult work and max only when justified. This configures newly created children, not existing children sent another message.
