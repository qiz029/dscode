# DSCODE 0.7.28

This release moves the whole `@deepseek-ai/dsh*` runtime from `0.1.5-rc.2` to `0.1.7-alpha.2` and carries DSCODE across the four upstream planes that release rewrote: configuration, agent presets, message attribution and the DeepSeek wire protocol.

- **Runtime pin (upgrade)**: every `@deepseek-ai/dsh*` dependency and override is now `0.1.7-alpha.2`, with `@deepseek-ai/cordis` at `4.0.4`, `@deepseek-ai/cordis-plugin-loader` at `1.0.5` and `@deepseek-ai/schemastery` at `3.18.4`, the versions that release requires. Five packages disappeared upstream and are replaced by their successors: `dsh-agent-presets` → `dsh-agent-preset` plus `dsh-agent-preset-registry`, `dsh-code-runtime{,-worker-thread}` → `dsh-ptc-runtime{,-node}`, `dsh-workflow-worker-thread` → `dsh-workflow-ptc`, and `dsh-settings-file` → `dsh-config-editor`. The upgrade brings upstream's `run_code` sandbox escalation, durable image offload, the MCP client on `@modelcontextprotocol/client` 2.0.0, subagent permission inheritance and compaction retry recovery. `0.1.7-alpha.2` is upstream's `alpha` channel, not a release candidate: it is the line upstream is developing, and a later alpha may move these interfaces again.
- **Configuration (breaking upstream API)**: DSH replaced settings sections with volatile configuration — a `.volatile()` field arrives as a reference the Settings form and a profile edit both write, and `settings.installSection` is gone. The OpenRouter and Grok routes now mark their editable fields volatile, read a snapshot per request, address their form by the profile entry id (`dscode-openrouter`, `dscode-grok`), and re-register the route from `loader/volatile-update` when the retry policy changes. `@anionex/dsh-computer-use` 0.3.2 still calls the older `ctx.settings.register`; DSCODE now mounts that bundle through its own `plugins/computer-use` row, which restores the method as a read-only view over the composition config before the provider's constructor runs. Nothing patches the installed package, so the repository and the npm bundle behave identically.
- **Agent presets (breaking upstream API)**: the registry reads declaration rows and no longer discovers presets from directories, and the shipped `standard`/`ptc`/`minimal` rows live in the `dsh-web-app` bundle this profile does not carry. `presets/dscode/agent.cordis.yml` therefore travels as one `@deepseek-ai/dsh-agent-preset` row inside the profile patch — rendered by `scripts/preset.mjs`, which indents the file as text so its `!!js` expressions and comments survive — and `dscode` is the only declared preset and the deployment default. Setup no longer materialises `.runtime/agent-presets/dscode`, and the npm bundle no longer ships a `presets/` directory. DSCODE already locked its mode to `dscode`, so the roster is unchanged in practice; a session recorded under an upstream preset still resumes and migrates, which `verify-runtime-foundations` covers.
- **Permission preset rename (breaking)**: DSH 0.1.7 reserves the name `auto` for its own Auto integration (full access with approval off) and refuses a configured preset of that name, so DSCODE's reviewed preset is now **`auto-review`** — the same `workspace-write` plus `approval: ask` bundle with the model reviewing eligible requests. Use `/permission auto-review`, `dscode exec --permission auto-review` and `permission: auto-review` in a trigger; the trigger gates still accept the old name for definitions written before this release. A session whose recorded preset is `auto` keeps its sandbox and approval values and shows as `custom` until it is switched.
- **Message attribution (breaking upstream API)**: the shared `plugin` source kind is retired — every producer declares its own `kind`, and session format v4 refuses a message that still carries the wrapper. DSCODE's injecting plugins now name themselves (`dscode-session-bridge`, `dscode-time-marks`, `dscode-shell-exec`, …), and one helper, `plugins/message-source/kind.mjs`, resolves all three shapes durable history can hold: the current kind, the pre-upgrade `{ kind: 'plugin', plugin: '<producer>' }`, and the `plugin:<producer>` kind the v3-to-v4 session migration writes. The terminal's transcript keys its hidden snapshots, reminder rows and relay rendering off that helper, so a resumed older session still renders as before. The bridge also moves from the retired `agent/session-start` event to `agent/created`, which 0.1.7 awaits at the same point; without that change every turn in a bridged session ended with "Session communication owner is not ready".
- **DeepSeek wire protocol (upgrade)**: the adapter now speaks the DeepSeek Messages API, where the system prompt is a request field and the effort rides in `output_config`. The Ultra patch was rewritten accordingly: Ultra is advertised in the model's effort catalog, normalised to the provider's `max` when the request is serialised, and the Ultra and Flash policies are appended to the `system` field by two new helpers in `plugins/ultra/policy.mjs` (the message-shaped pair stays for the OpenRouter and Grok adapters). Image offload follows upstream's new contract: a route reports how many oldest occurrences exceed its budget with `IMAGE_OFFLOAD_REQUIRED` and the `compaction-image-offload` executor records that choice durably, instead of each request dropping the oldest images on its own — DSCODE's OpenRouter adapter now does the same.
- **Computer Use (known limitation)**: `@anionex/dsh-computer-use` 0.3.2 restores its execution tools on resume by reading the durable log for the loaded skill, and it looks for the pre-0.1.7 shape — a `tool-result` content block carrying `toolCallId` and `isError` — which session format v4 moved onto the message. Live activation is unaffected, because that path reads the execution result: loading the `computer-use` skill exposes `computer_observe` and the rest as before, and the native helper handshake passes. A **resumed** session keeps the `computer_use_activate` bootstrap but regains the execution tools only once the skill is loaded again. The pinned package has no newer release; the harness probe records the behaviour as `HARNESS_PROBE_NOTE` instead of asserting a restoration this dependency cannot perform.
- **Pinned runtime patches (maintenance)**: `RUNTIME_VERSION` is `0.1.7-alpha.2`. Three of the nine patches needed new anchors — the subagent tool's recursion budget now comes from `subagents.resolveMaxDepth`, the bash tool's config schema is multi-line, and the DeepSeek adapter's ultra path was rewritten as described above — and all nine apply, parse and stay idempotent against the new tree.

Verification completed before tagging: `npm run check` passed on macOS (lint, both typechecks, 543 unit tests at 83.32% measured `.mjs` line coverage, the nine native Harness integration probes, both package tarballs and 51 evaluations), and the patched runtime was additionally re-validated by applying every patch twice and parsing the result. `npm run doctor` also passed against a real profile boot on the new tree: both the shipped `standard` and the DSCODE preset composed, 51 tools with scoped Chrome MCP discovery, skill activation, file editing and shell execution, the compaction provider, a nonempty session resume, the full auto-review allow/deny/human path with its audit, child worktrees and effort selection, manual compaction, and a healthy native Computer Use helper (`ready: true`, accessibility granted). `npm run verify:hub` passed too, after the same preset gap surfaced there: the installed
profile declares only DSCODE's preset, so the agent probe's `standard` mount failed until the
verification's overlay declared it from the `dsh-web-app` copy the installation carries. It
then verified the native locked Hub install, launcher first start, Hub doctor, the installed
bundle's agent loop, shell, subagent worktrees, auto review, compaction and telemetry, its
session messaging, cards and memory probes, and a failed upgrade with rollback. The
documentation checker prints clean.

What has no automated case here: the interactive TUI was not driven by hand for this release, so the terminal's own rendering of a 0.1.7 session is covered only by `tests/tui-render.test.mjs` and the typechecks; no paid provider request was made, so the Messages-API changes are proven against fixture streams rather than DeepSeek's live endpoint; and no desktop action was driven through Computer Use — its helper health and tool exposure are proven, its actual screen control is not.
