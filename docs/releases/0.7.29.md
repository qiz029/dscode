# DSCODE 0.7.29

This release adds the account plane DSH 0.1.7 introduced — a browser sign-in that authenticates the DeepSeek route without an API key — and repairs two composition rows the 0.1.7 upgrade left misaligned.

- **`/account` (new)**: sign the DeepSeek route in with a DeepSeek account through the system browser. `/account login` starts one attempt, `/account` reports whether a grant is stored plus the account identity, recharge wallets and — separately — bonus wallets and the platform's usage and top-up pages, `/account cancel` abandons an attempt in flight, and `/account logout` removes the grant from this machine. The flow is the upstream one: PKCE (S256), a `state` the provider compares in constant time, a one-time code exchange, and the grant committed to the same local credential store as the API keys. A signed-in machine needs no `DEEPSEEK_API_KEY`; a stored key stays the fallback, and a route pointed at a non-default base URL deliberately never receives the account token. The command's output carries no token — account state is the client-safe projection, and the token stays Host-only inside the LLM route. Every string is translated in all six interface languages. See [Account login](../account-login.md).
- **Loopback callback server (new)**: the account provider registers `/oauth/callback` on the Host's HTTP server, so the TUI profile now composes `@deepseek-ai/dsh-host-webserver` on `127.0.0.1` with an OS-assigned port. It carries **no route except while a sign-in runs** — the callback appears when an attempt starts and is removed when it settles — and this profile mounts none of the Web shell's frontend or API rows, so anything else answers 404 and a callback without a valid `state` and `code` answers 400. `DSCODE_ACCOUNT_LOGIN=0` removes the listener entirely; `/account login` then refuses with that reason and the other subcommands keep working.
- **Host-plane workflow engine (fix)**: DSH 0.1.7 renamed that row from `workflow-worker-thread` to `workflow-ptc`. A Loader patch addresses rows by id, so DSCODE's disable silently stopped landing and `workflowEngine` was published process-wide, exactly the leak the preset's entry-local realm exists to prevent. The disable now names the current id, and a new composition test checks **every** id DSCODE patches against the bundles this profile composes, so the next upstream rename fails in the suite instead of in a running session. The audit found no other stale target.
- **Redundant PTC runtime row (cleanup)**: 0.1.7 ships the Node PTC runtime in the base composition, and DSCODE's own insert carried the same id, so it only re-patched that row rather than mounting a second one. The insert is gone; `ptcRuntime` still resolves from the base row.

Verification completed before tagging: `npm run check` passed on macOS (lint, both typechecks, 558 unit tests at 83.87% measured `.mjs` line coverage, the nine native Harness integration probes, both package tarballs and 51 evaluations); `npm run doctor` booted a real profile; and `npm run verify:hub` passed the native locked install, launcher first start, Hub doctor, the installed bundle's agent, messaging, cards and memory probes, and a failed upgrade with rollback. The account flow was additionally exercised against the live platform without completing a login: `startSignIn` returned a real `platform.deepseek.com/dsh/authorize` URL, the loopback `/oauth/callback` route existed during the attempt and answered 400 without a valid `state` and `code`, and cancelling removed the route (404) and left the machine signed out. The twelve account unit tests drive the whole command with a service double, including the case that made the first implementation wrong: the authorize URL does not exist when `startSignIn` returns, so the browser is opened only after the URL is published. The composition test was mutation-checked by restoring the stale id, which fails it.

What has no automated case here: completing a sign-in in the browser needs a real account, so the callback, code exchange and grant commit are proven only by the provider's own contract and the live attempt up to the browser step; no paid provider request was made; and the interactive TUI was not driven by hand, so `/account` is covered by its unit tests and the command registration probe rather than by a rendered session.
